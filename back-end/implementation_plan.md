# Goal Description
Build an automated, highly varied database of communication Case Studies using the **Tree of Debate (ToD)** framework, branching from operations defined in `Nghiệp vụ khách sạn.pdf`. Since `STATE_SPEC.md` is no longer suitable, we will design a new data schema and loading mechanism tailored for ToD. This ensures Unity gets the visual/environmental data it needs, while the LangGraph Agent gets the deep persona and situational context generated by the debate.

## User Review Required

> [!IMPORTANT]
> **New Schema Design & Loading Mechanism:** We are completely replacing `STATE_SPEC.md` with a new ToD-centric schema. Please review the proposed `ToD_Schema` below. The workflow will be: 
> 1. Unity requests a scenario (e.g., "Check-in").
> 2. Backend fetches a leaf node from the ToD DB.
> 3. Backend sends `unity_init` to Unity and initializes the LangGraph Agent with `agent_init`.
> **Note:** As requested, environmental interactions (`interactable_props`) have been removed from the Unity data to reduce complexity for the demo.
> Does this structure and loading flow meet your expectations?

## Open Questions

> [!WARNING]
> 1. **Unity Communication:** Currently, does Unity poll the backend for the initial state via REST API, or is it pushed via WebSocket upon connection?
> 2. **ToD Tree Structure:** Should the DB store the *entire tree* (for tracing how a scenario was debated) or just the *leaf nodes* (the finalized, playable scenarios)? Storing just leaves is more efficient for runtime.

## Proposed Changes

We will introduce a new Data Model for ToD generated cases and a mechanism to distribute this state.

### 1. New Database Schema (`tod_case_schema.json`)

Each document in MongoDB will represent a finalized scenario (leaf node) generated by the Tree of Debate.

```json
{
  "_id": "tod_checkin_angry_001",
  "root_operation": ["Check-in", "Currency Exchange"], // Supports multiple/nested operations
  "debate_trace": ["Proposer: VIP late", "Critique: No room ready", "Refiner: Add Currency Exchange sub-goal"],
  
  "unity_init": {
    "environment": "env_reception_desk",
    "character_prefab": "char_vip_male_01",
    "initial_animation": "anim_tapping_watch_impatiently"
  },
  
  "agent_init": {
    "persona_name": "Mr. Viktor",
    "system_prompt": "You are Mr. Viktor, a VIP guest. You are extremely impatient because your room is not ready. You will NOT leave the reception desk. You demand to speak to the manager.",
    "knowledge_base": {
      "booking_info": "Booked via direct call, Presidential Suite, Paid 50% deposit.",
      "hotel_policy": "VIPs get immediate check-in or complimentary lounge access."
    },
    "win_condition": [
      { "id": "goal_1", "description": "Trainee calms guest down and checks them in." },
      { "id": "goal_2", "description": "Trainee successfully processes currency exchange." }
    ]
  },
  
  "transitions": {
    "on_success_next_case": "tod_escort_room_002", // To chain into the next logical operation
    "on_fail_next_case": "tod_complaint_manager_003"
  }
}
```

### 2. State Loading Mechanism

#### [NEW] `back-end/api_agent/services/state_loader.py`
This service handles loading the scenario from the ToD DB and splitting it.
- **For Unity:** Extracts the `unity_init` block and sends it via API/WebSocket. Unity uses this to instantiate the prefab and set up the scene.
- **For Persona Agent:** Extracts the `agent_init` block and injects it directly into the LangGraph state/system prompt before the conversation begins.

#### [NEW] `back-end/api_agent/tod_generator.py`
The offline generator script that reads `Nghiệp vụ khách sạn.pdf`.
- Generates scenarios using ToD logic.
- Formats the output exactly to the `tod_case_schema` JSON above.
- Saves directly to the MongoDB `tod_cases` collection.

#### [DELETE] `back-end/STATE_SPEC.md`
Remove the old state specification to avoid confusion, replacing it with documentation for the new ToD schema.
